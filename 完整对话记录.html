你你提问与需求

需求描述 企业内部多个业务系统在关键事件发生时，需要调用外部系统供应商提供的 HTTP(S) API 进行通知。

例如： 用户通过第三方广告系统引流并成功注册后，通知对应的广告系统 用户订阅付款成功后，通知 CRM 系统更改 Contact 状态 用户购买商品后，通知库存系统进行库存变更

不同供应商的 API： 请求地址不同 Header / Body 格式不同

业务系统本身： 不需要关心外部 API 的返回值 只需确保通知请求能够被稳定、可靠地送达目标 请设计并实现一个内部服务，接收业务系统提交的外部 HTTP 通知请求，并尽可能可靠地投递到目标地址。

先考虑一下，设计架构时应该着重考虑的问题

CCodex回复

这是一个新内部服务的架构设计问题。按你的要求，先分析设计重点，暂不进入实现。

我的理解是：业务系统提交通知后可以继续自己的流程，由这个服务负责持久保存、异步发送、失败重试和故障追踪。核心难点是：发生故障时，请求是否会丢失、是否会重复，以及如何恢复。

  1. 先定义“可靠送达”的含义

    需要区分三个结果：

    • 服务已接收：通知已经可靠持久化，服务承诺继续处理。
    • 目标已接受：收到了符合约定的 HTTP 响应。
    • 目标业务已完成：对方真正完成 CRM 更新、库存扣减等操作。

    业务系统不关心返回值，不代表通知服务不需要检查返回值。服务必须根据响应判断成功、重试或终止。有些供应商返回 HTTP 200，Body 里却表示失败。

    如果对方只提供异步受理接口，我们通常只能确认“目标已接受”，不能直接确认“业务已完成”。

  2. 请求从产生到投递，全链路如何避免丢失

    要逐段分析故障窗口：

    故障位置 需要解决的问题
    业务事务成功，但还没提交通知就宕机 业务侧可用事务 Outbox，把业务变更与待发送事件写入同一事务
    通知服务返回成功后宕机 必须先可靠持久化，再返回受理成功
    已保存任务，但没有成功加入队列 避免数据库与消息队列双写不一致，或提供可恢复的调度机制
    Worker 领取任务后宕机 使用租约、超时回收等机制，让其他 Worker 能接手

    **通知服务能承担的可靠性边界，通常从“持久化受理成功”开始。**业务事件发生到提交成功这一段，也需要调用方配合。

  3. 重复投递与幂等是最关键的取舍

    一个绕不开的场景：

    库存系统已经扣减成功，但响应在网络中丢失。通知服务看到超时，无法知道对方是否执行成功。

    重试可能重复扣减，不重试可能漏掉通知。仅靠发送方无法保证外部业务“恰好执行一次”。

    因此通常采用允许重复尝试的投递机制，配合目标端幂等，并区分两层去重：

    • 提交去重：业务系统重复提交通知时，使用稳定的通知 ID 避免创建多个任务。
    • 执行去重：多次发送使用同一个供应商认可的幂等键，避免重复产生业务效果。

    如果供应商不支持幂等，尤其是库存增减这样的操作，需要明确重复风险，并考虑查询核对、人工处理或调整接口形式。内部去重无法消除这个网络故障窗口。

  4. 失败如何分类，重试到什么时候

    不能把所有失败都立即重试：

    情况 通常的处理方式
    网络异常、超时、部分 5xx 按策略重试；注意结果可能不确定
    429 限流 尊重供应商的重试提示，降低发送速率
    参数错误、无效地址 通常停止自动重试，等待修复
    认证失败 刷新凭证或告警，避免反复无效调用
    HTTP 成功但业务失败 按供应商协议判断

    重试需要指数退避、随机抖动、最大尝试次数和最长投递期限。超过期限进入失败终态或死信队列，支持查询和人工重放。

    “尽可能可靠”应当意味着失败可见、记录可追踪、任务可恢复，而不是无限重试。

  5. 慢供应商或故障供应商不能拖垮整个服务

    一个目标持续超时，不应该阻塞其他目标的通知。因此需要考虑：

    • 按供应商或业务方限制并发和发送速率。
    • 设置连接超时、整体请求超时及响应大小上限。
    • 对持续故障的目标退避或熔断。
    • 控制积压、保护存储容量，并在必要时拒绝新请求。
    • 对不同业务方公平调度，避免一个大客户占满处理能力。

    这决定了系统在外部依赖故障时是否仍能正常运转。

  6. 是否需要顺序保证，以及通知是否会过期

    默认并行发送加重试，会导致乱序。例如“订阅成功”通知重试期间，“取消订阅”通知先送达，随后旧通知又把 CRM 状态改回去。

    要明确是否要求同一用户、订单或 Contact 的通知有序。若需要，通常按业务实体保证局部顺序；还要决定前一条失败时是否阻塞后续消息。

    同时，部分通知具有时效性，不能隔几天后仍按原意执行。顺序、版本号和过期策略需要结合业务语义确定。

  7. 通用 HTTP 投递与供应商适配的边界

    你描述的是“业务系统提交外部 HTTP 请求”，因此可以先把核心能力定义为接收 URL、Method、Header、Body 和投递策略。

    但需要提前考虑：

    • Body 是否要原样保存，避免重新序列化导致签名失效。
    • Token、签名、时间戳是否会在等待或重试期间过期。
    • 成功条件是否需要按供应商配置。
    • 供应商配置变更后，历史任务按哪个版本发送。

    **请求内容通常需要稳定保存，认证信息可能需要在每次发送时动态生成。**这会影响是否需要独立的供应商适配层。

  8. 安全、可观测性和容量目标

    接收 URL 并代发 HTTP 请求，意味着服务具有网络访问代理能力，需要调用方鉴权、目标地址限制、SSRF 防护，以及重定向后的地址校验。凭证和业务数据要加密保存、日志脱敏。

    运维上至少能回答：这条通知现在在哪里、尝试过几次、为什么失败、下次什么时候重试。关键指标包括投递成功率、投递延迟、积压数量、最老任务等待时间和供应商错误率。

    容量设计则需要明确峰值请求量、请求大小、可接受延迟，以及外部系统故障多久仍需保存并继续投递。重试流量也必须计入容量。

我会优先明确三个架构约束：**受理成功后如何不丢任务、目标能否安全接收重复请求、失败后如何恢复。**这三点确定后，再选择数据库任务表、消息队列或其他调度方案，技术选型才有依据。

CCodex回复

对，前面我把重点放在“投递执行”上，缺少了业务接入和配置管理这两层。你指出的三个问题会直接影响服务边界，应该先于队列、重试等技术选型考虑。

1. 供应商接口如何配置，才能让接入和维护方便

如果每个业务系统都要自己拼接供应商的 URL、Header、Body，这个服务承担的主要是可靠转发；供应商接口一旦变化，调用方仍需要修改代码。

更便于集中维护的方式是：业务系统上报统一的业务事件，由通知服务根据配置生成供应商请求。配置至少分为三类：

配置 负责什么 示例
供应商接口 地址、Method、认证、请求模板、成功判定、超时及重试策略 CRM 更新 Contact 接口
事件订阅 哪些事件需要通知哪个接口，以及触发条件 付款成功且来源为 A 时通知广告系统
字段映射 业务事件字段如何转换成供应商字段 user.id → contact_id

配置的便捷性也不能仅理解为“提供一个 JSON 编辑框”，还应考虑：

  • 支持模板复用、字段选择、必填项与类型校验。
  • 输入样例事件，可以预览生成的 URL、Header 和 Body。
  • 支持沙箱试发，明确区分预览与真实发送。
  • 配置具有草稿、发布、版本、回滚和变更审计。
  • 凭证独立管理，配置中引用凭证，避免复制明文密钥。

普通字段转换可用声明式配置；复杂签名或特殊协议通过适配器扩展，避免把配置系统做成任意脚本执行平台。

2. 业务事件和投递任务是两个不同的概念

一个事件表示“业务上发生了什么”，一条投递任务表示“需要向某个目标发送什么”。

例如：

订单支付成功事件
    ├─ 广告系统回传任务
    ├─ CRM 更新任务
    └─ 库存系统通知任务

因此需要显式的转换环节：

接收并持久化事件
    → 匹配订阅与条件
    → 字段映射、请求构建
    → 持久化投递任务
    → 调度执行

这里有几个容易遗漏的设计点：

  • 一对多关系：一个事件可以生成零到多个任务，各任务独立成功或失败。
  • 转换可恢复：事件保存成功后，即使转换进程宕机，也能恢复生成任务。
  • 任务生成幂等：同一个事件、同一条订阅、同一目标，重复转换不能产生重复任务。
  • 转换失败也是失败类型：缺字段、模板错误、找不到配置，应与 HTTP 投递失败分别记录和处理。
  • 配置版本固定：事件接受时或首次转换时，需要明确绑定哪个发布版本；重试不能悄悄采用新配置。
  • 重放语义明确：重发原任务与使用新配置重新转换事件，是两种操作，应分别提供。

通常可以保存任务的请求快照和配置版本，让重试保持业务内容一致；短期 Token 和时间签名在实际发送时生成。

3. “同步还是异步”需要拆成几个独立问题

业务方不关心供应商返回值，并不意味着提交事件时连“是否受理成功”都不需要知道。

环节 建议的默认方式 调用方获得什么
业务系统提交事件 HTTP 同步确认受理 持久化成功后返回事件 ID
事件转换成任务 异步处理 通过状态查询查看匹配、转换结果
执行外部 HTTP 请求 异步投递 通过状态查询查看各任务结果
业务方获取最终状态 按需查询；有需求再增加回调或结果事件 最终投递状态

这里还要区分：异步投递不等于 HTTP 请求“发出去就不管”。Worker 仍然需要等待响应或超时，才能更新状态并判断是否重试。

同步转换也有价值：可以在提交时立即反馈字段映射错误。但它会增加接入延迟，并让配置处理影响接口可用性。对于这类可靠通知服务，我倾向于：

接入时同步完成鉴权、事件格式校验和持久化；订阅匹配、请求构建和实际投递异步执行。

如果确实存在需要立即获取投递结果的场景，可以在同一套持久化任务流程上增加“限时等待结果”模式。等待超时后返回任务 ID，任务继续执行，不能把调用方等待超时直接视为任务失败。

所以，架构边界应调整为：

配置管理 → 事件接入 → 事件路由与转换 → 投递调度与执行 → 状态查询与运维。

同时需要明确一个产品定位：**业务方提交业务事件，还是提交已经构建好的 HTTP 请求。**前者集中管理供应商差异，后者接入更直接。结合你提出的配置便捷性，适合以事件接入为主，必要时保留原始 HTTP 任务入口，让两种入口最终复用同一套投递能力。

你你提问与需求

接收事件、转换成投递任务，最后以HTTP请求的方式执行，也就是事件、任务、执行三块。并且可以观测他们的转换。这样拆分是否过度，在执行层遇到异常时，是否应该一路穿透回事件，标记一整条线的异常。失败重试时，应该遍历任务块，还是执行块。

CCodex回复

这个拆分是合理的，事件、任务、执行分别表达业务事实、投递意图和发送过程。不过，建议把“执行”具体定义成“执行尝试”：一个任务重试多次，就会产生多条执行记录。

它们可以先放在一个服务、一个数据库里，不必拆成三个独立服务。

1. 三块各自负责什么

对象 含义 主要记录
事件 Event 发生了一件需要通知的业务事情 事件内容、转换状态、生成了哪些任务
任务 Task 需要向某个目标完成一次通知 目标、请求内容、投递状态、重试策略、下次执行时间
执行尝试 Attempt 为完成某个任务，实际发起了一次 HTTP 调用 开始与结束时间、响应、异常、耗时

关系是：

事件 E1
 ├─ 任务 T1：通知 CRM
 │   ├─ 执行 A1：超时
 │   └─ 执行 A2：成功
 └─ 任务 T2：通知广告系统
     └─ 执行 A3：成功

这里三层都有独立价值：

  • 事件回答：“这件业务事情有没有被处理，应该通知谁？”
  • 任务回答：“这个目标是否已经通知成功，还要不要继续？”
  • 执行记录回答：“具体尝试过什么，为什么失败？”

如果把任务和执行记录合并，每次重试覆盖结果，就容易丢失历史；如果每次重试都创建一个新任务，又不容易判断原来的通知是否已经完成。

2. 执行异常应该向上可见，但不应该一路标成失败

应区分一次尝试失败和整个任务最终失败。

例如第一次 HTTP 超时：

层级 应呈现的状态
执行尝试 本次超时，目标是否执行可能未知
任务 等待重试
事件 投递进行中，可以看到一个任务正在重试

重试成功后：

层级 应呈现的状态
执行尝试 第一次超时、第二次成功，历史保留
任务 成功
事件 所有目标完成后，汇总为完成

因此，异常信息要能沿链路追踪，终态失败不能直接沿链路复制。

事件层最好分开呈现两个维度：

  • 转换状态：待转换、转换中、转换完成、转换失败。
  • 投递汇总：生成几个任务，成功几个，处理中几个，最终失败几个。

例如：“转换完成；3 个任务，2 个成功，1 个等待重试”，比单一的“事件异常”准确得多。

只有任务不再自动重试、进入最终失败时，事件的汇总才应体现最终失败。多个任务结果不同时，应允许“部分成功”。事件没有匹配订阅，也需要明确显示“无须投递”，避免看起来一直未完成。

还需注意：只有任务生成已经完成，才能判断事件的整体投递是否完成，否则可能把“当前已生成的任务都成功了”误认为整个事件完成。

3. 重试应该由任务层驱动，执行层负责留下记录

建议职责如下：

任务决定“是否重试、何时重试”；执行器负责发请求；执行记录保存每次尝试的事实。

基本流程是：

领取到期任务
  → 创建一次执行记录
  → 发起 HTTP 请求
  → 记录本次结果
  → 更新任务：成功 / 等待重试 / 最终失败
  → 更新事件的投递汇总

不建议通过遍历失败的执行记录来决定重试，因为：

  • 同一个任务可能有多条失败执行记录，容易重复调度。
  • 某条历史执行失败后，任务可能已经重试成功。
  • 执行记录描述过去，不能代表任务现在是否需要继续处理。

如果采用数据库调度，应该按索引领取：

状态为待执行或等待重试
并且 next_attempt_at <= 当前时间

这不是全量遍历任务。使用队列时也一样：队列负责唤醒，任务状态负责确认当前是否仍允许执行。

4. 宕机恢复也以任务为入口

普通 HTTP 失败可以正常记录结果并安排重试，但执行器宕机时，可能来不及更新任何状态。

因此任务需要领取租约或执行超时机制。恢复程序找出租约过期的执行中任务，标记其未完成尝试为“中断或结果未知”，再按策略重新调度。多个执行器之间还要通过原子领取、版本校验等方式避免同时处理和旧执行器覆盖新状态。

但租约不能消除“对方已成功、我方没记录”的窗口，所以重试仍需要供应商幂等能力配合。

我的建议是保留三层模型：**事件负责转换与整体追踪，任务负责投递状态与重试，执行尝试负责过程证据。**事件上的投递汇总可以先查询计算，量大后再异步维护，不必为了可观测性让每一次发送都同步更新整条链路。

      contact_id: string
      paid_at: datetime

CCodex回复

仍然可以异步处理。异步描述调用方是否等待，顺序依赖描述任务何时允许执行，两者并不冲突。

你需要的是“有依赖关系的异步任务”，可以把它理解为持久化的链式调度。例如：

付款成功事件
    ├─ A：在 CRM 创建 Contact
    │    └─ B：更新 Contact 为付费用户
    │         └─ C：通知另一个供应商开通服务
    └─ D：通知广告系统

业务系统提交事件后即可返回。A 和 D 可以并行；B 必须等待 A 成功；C 必须等待 B 成功。执行器不需要一直占着线程等待整条链结束。

在原来的“事件、任务、执行尝试”模型中，增加任务依赖即可。

对象 增加的职责
事件 关联本次生成的任务及依赖关系，汇总整体进度
任务 保存前置依赖，判断是否具备执行条件
执行尝试 仍然只记录一次具体 HTTP 调用

任务可以有这些状态：

等待依赖 → 待执行 → 执行中 → 成功
                        ├─ 等待重试 → 待执行
                        └─ 最终失败

A 成功后，调度器检查 B 的前置条件，将 B 从“等待依赖”变为“待执行”。整个过程依靠持久化状态推进，而不是在内存里写一个长时间运行的 A → B → C 调用函数。

需要进一步明确几个规则：

  1. 什么叫前置任务“成功”

    如果 A 返回 HTTP 202，只表示对方已受理，而 B 必须等待对方实际完成，那么不能立即释放 B。A 还需要通过回调或轮询确认完成，之后才能满足依赖。这一点比同步还是异步更关键。

  2. 后续任务是否需要前序结果

    例如 B 需要使用 A 返回的 contact_id。这时服务必须提取并持久化 A 的必要输出，再用于构建 B 的请求。

    这也意味着：可以先创建 B 的任务和依赖关系，但不能要求在事件转换阶段就生成 B 的完整 HTTP 请求。部分参数需要等依赖完成后才能确定。

  3. 前序失败时，后续怎么办

    A 等待重试时，B 保持等待；A 最终失败时，B 应标记为“依赖失败而阻塞”或按策略跳过，而不是标记成“HTTP 调用失败”，因为它根本没执行。

    如果 A、B 已成功而 C 失败，默认只重试 C，不重新执行整条链。是否需要撤销 A、B 的效果，是额外的业务补偿问题。

  4. 推进依赖本身也要可靠

    要防止“A 已记录成功，但还没唤醒 B 就宕机”。可以用事务内更新、可靠事件或定期扫描满足条件的任务来恢复。重复唤醒也不能导致 B 被重复领取。

  5. 依赖配置需要固定版本

    如果后台可以动态调整顺序，已开始执行的事件应该默认继续使用原来的依赖图；新配置影响新事件。发布时检查依赖是否成环、引用是否有效、前序输出能否满足后序输入。

所以，这里的变化是：**原先的任务列表，升级成了任务依赖图。**如果始终只有线性顺序，用简单的步骤链就够；出现并行分支、多个前置任务汇合时，再采用有向无环图（DAG）。

建议先支持最小能力：成功后触发下一步、独立任务并行、失败重试、依赖阻塞、必要输出传递。这些仍然可以在一个服务内实现；只有流程进一步涉及长时间等待、复杂分支、人工审批和补偿时，再评估专门的工作流引擎。

1. 系统目标与边界

系统接收业务事件，并按规则向供应商发送 HTTP 请求。

业务系统只需向统一的 HTTP 接口提交事件。业务系统不需要知道供应商列表，也不需要接收供应商的处理结果。

分发系统负责保存事件、生成任务、执行请求和处理失败。

供应商负责执行自己的业务操作。分发系统不保证供应商内部业务一定成功。

2. 核心实体

系统定义三个核心实体：

实体 定义
事件 上游提交的业务事实，例如下单或取消订单
投递任务 针对一个供应商业务目标生成的工作单元
请求步骤 完成任务所需的一次逻辑 HTTP 操作，由供应商 Driver 实现

一个事件可以生成多个投递任务。一个投递任务可以包含多个请求步骤。

每个请求步骤可以执行多次。系统必须保留每次执行的结果，不能用新结果覆盖历史记录。

事件、任务、请求步骤和执行记录必须能够关联查询。

3. 接收与持久化

系统必须先将事件写入 MySQL，再向上游返回受理成功和事件 ID。

上游提交失败或超时时，可以使用同一个事件 ID 再次提交。系统必须识别重复提交。

MySQL 保存事件、任务、请求步骤、配置版本和执行记录。Redis 用于异步队列、调度和限流。

Redis 队列丢失或 Worker 重启后，系统必须能根据 MySQL 中的记录恢复未完成工作。

本系统的可靠性承诺从持久化受理成功开始。事件提交成功之前的可靠性由上游负责。

4. 异步处理与运行隔离

系统使用 Laravel 常驻队列 Worker 异步处理事件和任务。

单个供应商超时或故障时，不应阻塞其他无依赖的任务。系统应按供应商限制并发、请求速率和资源占用。

存在前置依赖的任务可以等待。无依赖的任务可以并行执行。

5. 供应商与配置管理

系统通过统一 Driver 接口接入供应商。各 Driver 实现供应商的认证、签名、请求构建和响应解析。

一个供应商可以提供多个 API 操作。多个账号或环境可以复用同一个 Driver。

配置管理应支持：

  • 供应商连接、API 操作和凭证引用。
  • 事件订阅、触发条件和字段映射。
  • 请求顺序、执行时间和重试策略。
  • 配置启停、版本管理、校验和回滚。

系统必须区分两类顺序要求：

  • 跨事件顺序：同一订单的下单事件应先于取消事件处理。
  • 执行依赖：库存扣减成功后，才能发送订单确认短信。

系统应使用业务实体 ID 和业务序号等信息判断跨事件顺序，不能只依赖请求到达时间。

7. 投递语义与重试

系统采用至少一次的投递方式，允许重复请求。

系统在规定的次数或时间内自动重试。超过限制后，保留失败记录，停止自动重试，并发出告警。因此，系统不承诺在有限时间内一定投递成功。

重试在请求步骤层执行。某一步失败时，默认只重试该步骤，不重新执行整个任务。

系统应区分临时失败、永久失败和结果未知。各 Driver 应定义成功条件及可重试错误。

8. 幂等与结果核对

同一请求步骤的所有重试应使用同一个幂等键。不同请求步骤应使用不同的幂等键。

对库存变更等高风险操作，系统应优先使用供应商的幂等和状态查询能力。请求结果未知时，应按接口规则先查询，再决定是否重试。

9. 故障恢复与人工操作

系统必须支持重复运行和中断恢复。

Worker 中断后，系统应回收超时的执行占用，并重新判断任务是否可以执行。恢复过程不得直接重跑所有已成功步骤。

供应商持续失败时，系统应停止密集重试，进入熔断状态，并定期探测恢复情况。

系统应限制重试速率、队列积压和存储占用。容量不足时，系统应明确拒绝新请求，不能返回虚假的受理成功。

只有预先配置了业务等价且可安全切换的替代接口，系统才允许切换。原请求结果未知时，不应盲目调用替代接口。
